# Interactive Study BOOX — 产品需求文档

> 版本：v0.7
> 更新日期：2026-09-05
> 状态：P0/P0.1 已完成；P1 本地学习库、手动 GitHub 同步和 VPS HTTPS 远程阅读链路已完成；P2 远程 WebView APK Release 版已构建；项目暂时归档，进入真实学习观察期

## 1. 一句话描述

这是一个面向个人使用的 Markdown 互动式学习阅读工具：P0 在电脑或局域网内读取本地学习库，P1 通过常驻 VPS 让手机和 BOOX 随时访问同一份学习内容，并在文章末尾提交反馈，由 AI 根据学习计划、当前文章和反馈生成下一篇文章。

## 2. 背景与问题

用户习惯使用电纸书阅读，但希望保留 dontbesilent 互动式学习的核心循环：

```text
准备学习材料 → 阅读一篇文章 → 写下反馈 → AI 生成下一篇 → 继续阅读
```

电脑适合整理文件、准备原材料和管理学习项目；BOOX Leaf 5 适合作为轻量的阅读和反馈终端。因此第一版不试图让电纸书承担复杂的文件管理工作。

## 3. 目标用户

- 只有一个主要用户：本人。
- 主要设备：电脑和 BOOX Leaf 5。
- 主要内容格式：Markdown 文件。
- 主要输入方式：BOOX 系统自带的语音转文字，应用只提供标准文本输入框。

## 4. 产品原则

- 先完成一个可以真实使用的最小闭环。
- 学习内容以 Markdown 文件为主要来源和保存格式；P0 使用本地文件夹，P1 使用 VPS 上私有仓库的工作副本。
- 应用负责阅读、反馈和生成；复杂的素材整理和项目归档仍由电脑完成。
- 阅读界面优先考虑电纸书体验，而不是视觉装饰。
- 不把中途问答强制变成学习记录。
- 不把“提交反馈”自动解释为“完成课程”。
- GitHub 同步由用户主动触发，不在每次文件修改时自动提交或推送。

## 5. 第一版目标

第一版 Prototype 至少能够完成以下流程：

1. 用户指定一个本地文件夹作为学习库。
2. 应用读取学习库中的 Markdown 文件并展示为可阅读的文章页面。
3. 用户浏览学习库中的真实文件夹树和 Markdown 文章。
4. 用户打开并阅读一篇文章。
5. 用户在文章末尾输入反馈，可以使用 BOOX 自带语音转文字。
6. 用户点击“提交并生成下一篇”。
7. 应用先把反馈追加保存到当前 Markdown 文件。
8. 后端读取学习计划、当前文章、反馈和映射的 `sources/` 原文，调用 AI 生成下一篇 Markdown。
9. 应用直接把下一篇文章保存到当前项目文件夹。
10. 页面停留在当前文章，只提示下一篇文章的名称；用户自行决定何时打开下一篇。

### 5.1 P1 远程可用版本目标（暂定）

P0 的本地模式验证完成后，P1 目标是让用户不必保持自己的电脑开机：

1. Node.js 后端部署在具有持久化磁盘的 VPS 上。
2. VPS clone 私有的 `learn-everything` 学习资料仓库，作为当前学习工作区。
3. 手机、BOOX 和电脑浏览器通过 HTTPS API 访问同一个后端和工作区。
4. 用户提交反馈和生成文章的流程保持不变，前端不直接接触 OpenAI API Key 或 GitHub 凭据。
5. 用户点击“同步到 GitHub”后，后端把自上次同步以来允许同步的 Markdown 修改合并为一个 commit，再推送到私有仓库。
6. GitHub 同步发生冲突或 VPS 不可用时，不强行覆盖文件，并向页面返回可理解的错误。
7. 远程访问必须有访问保护；正式方案使用 HTTPS + 应用内单用户登录，Nginx 只负责反向代理。

P1 仍然是单用户、自部署优先的方案，不引入多用户账号、支付或复杂云端数据服务。

P1 的本地同步闭环已经完成验证：程序可以读取配置的 `learn-everything` 工作区，识别允许同步的 Markdown 修改，由用户主动触发一次 commit 并推送到私有 GitHub 仓库。中文目录路径、被拦截文件和远程领先保护均已完成基本验证。VPS HTTPS、远程阅读和手机/BOOX 访问已经验证；正式开始学习前仍需再做一次远程反馈、生成和同步端到端回归。

## 6. 学习库与文件结构

### 6.1 学习库

P0 中，学习库类似 Obsidian 的 Vault，是用户指定的一个本地文件夹。它不是数据库，也不是必须部署在线上的服务器。

P1 中，学习库的角色由 VPS 上的一个 Git 工作副本承担。当前未同步的修改保存在 VPS 的持久化工作区；点击同步后，已提交版本保存到私有的 `learn-everything` 仓库。GitHub 仓库保存的是学习资料的版本历史，不是应用代码仓库，也不替代后端的运行时操作记录。

公开的 `interactive-study-boox` 仓库只保存程序代码和文档；真实学习资料放在私有的 `learn-everything` 仓库中。客户端只请求 VPS 后端，不直接把 GitHub Token 或 OpenAI API Key 放进浏览器或 APK。

首次使用时，应用需要让用户选择学习库根目录，并在之后记住这个位置。学习库位置应当可以在设置中更换。

### 6.2 文件夹结构

```text
学习库/
├── yet-to-start/
│   └── Thinking, Fast and Slow/
│       ├── sources/
│       │   ├── 00-contents.md
│       │   └── part-1/
│       │       └── 01-the-characters-of-the-story.md
│       ├── 00-原文索引.md
│       ├── 00-学习计划.md
│       └── 01.md
├── on-going/
│   └── 维特根斯坦十讲/
│       └── 学习课题/
│           └── 维特根斯坦第九讲：驳斥罗素的归纳理论/
│               ├── 00-学习计划.md
│               ├── 01.md
│               └── 02.md
└── archived/
    └── 阿德勒心理学/
```

应用展示用户已有的真实目录层级：文件夹可以继续嵌套，列表中只显示 `.md` 文件。应用不因自己的分类假设而重命名、创建、删除或覆盖用户已有的文件夹和文件。

### 6.3 项目状态管理

- `yet-to-start`、`on-going`、`archived` 是当前学习库采用的顶层整理习惯；应用将它们当作普通文件夹树的顶层节点，而不是写死的程序枚举值。
- 项目在不同顶层文件夹之间的移动仍是电脑端的手动操作。
- 第一版不根据阅读行为自动改变项目分类。
- 第一版不记录文章的“已完成/未完成”状态。

## 7. 功能需求

### 7.1 启动与继续阅读

- 打开应用后，优先显示上次打开的学习项目或文章。
- 如果保存了该文章的自动续读位置，打开并完成 Markdown 渲染后，应回到接近上次离开的位置。
- 可以继续浏览学习库中的其他项目和文章。
- 自动续读只服务于“继续阅读”，不显示为阅读进度，也不等于记录课程完成状态。

### 7.2 Markdown 阅读

- 应用读取原始 `.md` 文件。
- 阅读页面将 Markdown 渲染为适合阅读的内容，不要求用户面对原始 Markdown 符号。
- 第一版不要求在阅读页面直接编辑整篇原始 Markdown。
- 用户仍可使用 Obsidian、Codex 或其他编辑器直接修改文件，应用下次读取最新内容。

### 7.3 文末反馈

- 当前文章末尾显示一个标准文本输入框。
- 用户可以输入：理解了什么、哪里没看懂、卡住的位置、难度感受和希望继续学习的方向。
- 语音转文字由 BOOX 系统输入法提供，应用不自行实现语音识别。
- 反馈保存到当前文章的 Markdown 文件末尾，例如：

```markdown
---

## 学习反馈

这里是用户的反馈内容。
```

### 7.4 生成下一篇文章

- 用户主动点击按钮后才开始生成，不自动生成。
- 按钮文案暂定为“提交并生成下一篇”。
- 应用使用固定的提示词模板，不要求用户手动 `@` 文件。
- AI 生成所需的主要输入为：
  - 当前项目的 `00-学习计划.md`；
  - 当前正在阅读的文章；
  - 用户刚刚提交的反馈。
- 书籍项目还读取学习计划映射的 `sources/` 原始材料；一次生成只读取当前需要的文件，不发送整本书。
- 生成成功后，直接创建并保存下一篇 Markdown 文件。
- 默认按项目现有文章编号递增，例如 `01.md` 后生成 `02.md`。
- 生成成功后不自动打开新文章，只提示新文件名称或提供打开入口。

### 7.5 书籍学习项目初始化

书籍项目在进入互动学习前，先完成以下准备：

1. 将原始书籍拆分为 `sources/` 下的 Markdown 文件；
2. 生成 `00-原文索引.md`；
3. 生成 `00-学习计划.md`，并记录学习文章与原文的映射；
4. 生成第一篇学习文章。

一篇学习文章可以对应多个原文文件。原始材料与 AI 生成文章分开保存，原始文件默认不由学习流程改写。

### 7.6 失败处理

- 调用 AI 前先保存用户反馈，避免生成失败导致反馈丢失。
- AI 调用失败时，不创建空白文章。
- 页面提示失败原因，并允许用户重新生成。
- 重试时不应重复追加同一份反馈。

### 7.7 远程学习库与手动 GitHub 同步（P1：本地闭环与 VPS HTTPS 访问已验证）

- 后端使用配置的学习工作区路径；P0 可以是电脑上的本地文件夹，P1 默认是 VPS 上 `learn-everything` 的 clone。
- AI 生成、反馈追加和学习计划更新先写入工作区，不自动创建 Git commit。
- `GET /api/sync/status` 显示未同步文件、当前分支、远程是否领先以及是否存在冲突。
- 用户点击“同步到 GitHub”后，后端只把允许同步的学习 Markdown 文件加入暂存区，创建一个 commit 并推送。
- `.env`、API Key、Git 凭据、`node_modules/`、构建产物和运行时操作记录不得进入学习资料仓库。
- 如果远程仓库已经有 VPS 未拉取的修改，或者工作区存在无法安全判断的冲突，后端返回冲突状态，不执行强制覆盖。
- 本地同步闭环已经完成真实验证：中文路径下的 Markdown 修改能够被识别并成功推送；同步 UI 与中文路径修复已经合并到程序仓库 `main`。
- VPS 部署、Nginx Basic Auth、HTTPS、systemd 自动启动和私有学习库读取链路已经验证；正式开始学习前仍需复核远程 AI 生成和同步链路。

### 7.8 单用户应用登录与记住登录（已实现，生产启用待定）

- 这是面向本人的单一应用密码，不是多用户账号系统。
- 服务端设置 `AUTH_ENABLED=true` 后，登录页才会出现；默认关闭，因此不会改变现有本地或临时部署行为。
- 用户可以选择在当前设备记住登录；勾选时会话默认有效 7 天，未勾选时为较短的浏览器会话。
- 密码只以 scrypt 哈希保存于服务端环境变量 `AUTH_PASSWORD_HASH`，明文密码、哈希和会话令牌不进入前端、Markdown 或 Git。
- 登录成功后使用 HttpOnly 会话 Cookie；会话哈希和过期时间写入服务端 `AUTH_SESSION_FILE`，退出登录会使当前会话失效，服务重启后仍可恢复未过期会话。
- 当前 MVP 没有网页内修改密码按钮；更换密码通过服务端重新生成哈希并替换环境变量完成。它只影响应用登录，不影响 AI、GitHub、域名、备案或 Nginx Basic Auth 凭据。
- 生产环境已具备 HTTPS；认证迁移后 VPS 使用应用内单用户登录，APK 不保存密码，也不再依赖原生 Basic Auth 弹窗。

## 8. 电纸书友好要求

- 黑白或灰阶视觉，不依赖颜色传递关键信息。
- 单栏、清晰、适合窄屏阅读。
- 不使用动画、转场、视频、视差或复杂特效。
- 不使用依赖悬停状态的交互。
- 触摸目标足够大，文字和按钮清楚。
- 页面加载和 Markdown 渲染尽量轻量。
- 电脑端先验证功能，但界面从一开始就按 BOOX Leaf 5 的性能和屏幕条件设计。
- 后续在 Leaf 5 真机上验证系统语音输入、触摸和页面刷新表现。

## 9. 第一版明确不做

- 阅读时长统计。
- BOOX 官方阅读数据或 Neo Reader 集成。
- 文章已完成/未完成状态。
- 阅读进度百分比和学习数据报表。
- 中途问答历史、未解决问题管理和自动课程拆分。
- 多用户账号体系、细粒度权限、支付和社交功能；P1 允许为本人提供一个共享密码的单用户应用登录，但它不扩展为多用户系统。
- 复杂的文件移动、归档和素材整理工作。
- 24 小时运行的个人 AI 服务器。
- 把学习库和 AI 能力复制进 APK；学习内容仍以 VPS 上的 Markdown 工作区为真源。

这里的“第一版”指 P0/P1 的 Web 阅读器与远程服务。P2 的 APK 不是另一个独立后端，而是一个加载 `https://www.maki3991.xyz` 的全屏 Android WebView 外壳。

### 9.1 P2 Android WebView APK 范围（已确认，首版已实施）

- APK 安装后作为独立应用打开，不跳转系统浏览器，不显示地址栏、主页键、书签栏或浏览器工具栏。
- APK 只负责原生外壳、沉浸式阅读、返回行为和下拉刷新；网页、AI、学习资料和 Git 同步继续由 VPS 提供。
- APK 通过 HTTPS 加载远程网站，不把 `client/dist` 固定打包进 APK，因此普通网页、后端和学习资料更新不需要重装 APK。
- 网络不可用或 VPS 不可用时，APK 不承诺离线阅读。
- 第一版不上传 Google Play，只生成签名 APK 并手动安装到本人 BOOX。
- 不把应用登录密码、GitHub Token 或 AI API Key 写入 APK；登录由远程网页通过 HTTPS Cookie 处理。
- 必须保存 APK 的签名密钥；原生外壳更新时继续使用相同包名和签名密钥。

### 9.2 当前归档口径

当前版本已经足够开始正式的个人学习，不把分页、离线阅读、应用内登录迁移或其他增强功能作为启动前置条件。项目暂时停止新增功能，进入真实使用观察期：先在网页或 BOOX APK 中学习，只有出现可复现的问题或确实需要改变 Android 原生外壳时，再重新打开开发。

VPS 上的网页、后端和 `learn-everything` 学习资料更新后，重新打开 APK 即可生效，不需要重新打包；只有原生外壳、包名、签名或系统交互发生变化时，才需要重新构建并安装 APK。

## 10. 原型阶段的暂定实现方向

- 先在电脑端运行 Web 原型。
- P0 使用本地后端读取和写入用户指定的学习库文件夹。
- P1 使用同一套后端逻辑读取和写入 VPS 上配置的学习工作区；该工作区暂定为私有 `learn-everything` 仓库的 clone。本地工作区版本已经完成验证，VPS 临时版本也已部署并验证基本阅读链路。
- Markdown 文件仍然是学习内容的主要数据源；GitHub 只在用户主动同步时保存版本。
- P0/P1 暂不引入数据库，应用配置、操作记录和同步状态分别使用简单配置、服务端运行记录和 Git 状态。
- P2 使用 Capacitor Android 外壳加载远程 HTTPS 网站；原生层负责沉浸式全屏、下拉刷新、返回行为和必要的 BOOX 触摸适配。
- P2 不复制学习库，不在 APK 中保存服务端凭据；普通 Web/API/学习资料更新仍通过 VPS 部署完成。
- 客户端不直接调用 GitHub 或 AI 服务；这些凭据只保存在后端运行环境。生产环境当前使用 HTTPS + Nginx Basic Auth，APK 通过原生回调处理认证；后续可再迁移到应用内单用户登录。

以上技术方向仍属于暂定方案，最终实现方式记录在 `docs/ARCHITECTURE.md`。

## 11. 第一版验收标准

当以下条件全部满足时，第一版可以认为“至少能用”：

- 可以选择并记住一个本地学习库文件夹。
- 可以递归展示学习库中的文件夹和其中的 Markdown 文件。
- 可以渲染并阅读一篇 Markdown 文章。
- 重新打开应用后，可以回到上次打开文章的接近阅读位置。
- 可以在文章末尾输入反馈并保存回原文件。
- 点击按钮后可以调用 AI 生成下一篇文章。
- 下一篇文章会直接保存到正确的学习项目文件夹。
- 生成完成后当前文章不会自动跳走。
- AI 失败时已有反馈不会丢失，也不会产生空白文件。
- 页面在电脑浏览器中可用，并且没有明显依赖动画或复杂视觉效果。

### P1 远程访问与同步验收标准（暂定）

以下本地同步验收项已经完成：

- 本地后端可以从配置的 `learn-everything` 工作区读取学习资料。
- 用户主动点击同步后，多份 Markdown 修改可以合并为一个 Git commit 并推送到私有 GitHub 仓库。
- 中文目录路径可以正常识别；不允许同步的文件和远程领先状态不会被强制覆盖。

以下远程部署验收项已经完成基本验证，正式开始学习前再做一轮回归：

- 关闭个人电脑后，手机或 BOOX 仍能通过 HTTPS 打开 VPS 上的阅读器。
- VPS 能从私有 `learn-everything` 工作区读取目录、文章、反馈和学习计划。
- AI 生成结果和反馈能先安全写入 VPS 工作区；正式开始学习前再做一次回归。
- 用户点击同步后，多份 Markdown 修改只产生一个清晰的 Git commit 并成功推送。
- 页面能够显示未同步状态；远程领先、网络失败或冲突时不会强行覆盖学习资料。
- OpenAI API Key、GitHub 凭据和服务端绝对路径不会出现在客户端响应、APK 或公开代码仓库中。

- 修改原生外壳时可以使用同一个包名和签名密钥生成覆盖更新版本。

### P1 访问保护验收标准（暂定）

- 应用登录关闭时，现有开发和临时部署行为保持不变。
- 应用登录开启时，未登录用户不能读取学习库、文章、反馈、生成和同步接口；健康检查与登录状态接口仍可用于启动判断。
- 登录、退出、记住 7 天和会话失效行为在本地已验证；密码只保存为服务端哈希。
- 生产环境已具备 HTTPS；应用登录会话通过 `AUTH_SESSION_FILE` 持久化，服务重启后不应要求重新登录，除非会话已过期或运行时文件不可读。

## 13. 文章内标记与批注（P1，第一阶段）

正式学习时，用户可以在当前编号学习文章中选中普通段落的一段文字，并通过悬浮操作栏添加三类自有标记：

- 波浪线：表示“这里暂时不理解”，可以单独存在。
- 高光：表示“这里重要或喜欢”，第一阶段只保存并显示，不参与是否推进或补充的判断。
- 批注：保存用户自己的理解、疑问或联想，可以单独存在，也可以和波浪线或高光共存。

标记不写入数据库，而是写回当前课程 Markdown：正文中使用带 `data-study-id` 的自有 `span` 标记，文件末尾使用隐藏 JSON 元数据保存标记类型、原文片段、位置和批注。网站负责把它们渲染成波浪线、浅灰高光和可点击的批注角标；暂不承诺与 Obsidian 插件格式完全兼容，也暂不实现标记导出。

第一阶段只开放同一普通段落内的选择，不支持跨段、代码、链接、列表、复杂内联格式和重叠标记。数据模型使用 `segments` 数组保留多个片段，后续可以在不更换存储格式的情况下扩展跨段选择。

生成下一篇文章时，波浪线和批注作为当前文章的主动学习信号传给 AI；高光会作为“重要/喜欢”的弱信号提供，但默认不被当作已经理解或应该推进的证据。
